# 中文结构地图

目标：把中文文案生成从“润色”和“黑名单替换”提升为结构重组。主线永远是句法骨架：主语、谓语、宾语、定语、状语、补语和结果先成立，再处理语体、平台和风格。

本文是总地图，只做融合和路由，不替代现有 reference。细则仍回到对应文件：

- 句法骨架看 `chinese_sentence_structure.md`。
- 口语省略看 `colloquial_sentence_structure.md`。
- 语体选择看 `register_selection.md` 和 `chinese_register_modes.md`。
- 翻译腔和 AI 腔看 `anti_translationese_patterns.md` 与 `blacklist_patterns.md`。
- 技术项目介绍看 `technical_project_copy.md`。
- 批次重复看 `batch_repetition_review.md`。

## 0. 总流程

触发：任何中文介绍、报告、README 摘要、工具推荐、社媒文案、教程或对话回复。

判断：中文自然度不能只靠词表。先确认事实，再重排信息，把已知错误排除在候选空间之外，然后生成句子。validator 用来证明候选稿没有偏航，不能充当事后擦除器。

改法：

```text
事实材料
-> prompt 合同门禁
-> 中文事实稿
-> 事实稿门禁
-> 句法骨架分析
-> 句法门禁
-> 信息顺序重排
-> 语篇推进
-> 语体选择
-> 已知错误生成禁区
-> 正文稿
-> 结构标注稿
-> hard validator
-> 命中已知错误则废弃候选稿
-> 重新从中文事实稿生成
-> 通过后交付
```

优先级：

```text
主谓宾结构分析 > 信息顺序 > 语篇推进 > 语体距离 > 翻译腔 / AI 腔拦截 > validator
```

### 0.1 硬门禁流程

触发：任何中文生成、改写、即评、报告、README 摘要、工具推荐或对话回复。

判断：规则如果只停在提醒层，模型会回到旧句式。生成流程里的每一段都要有明确 pass / fail；没有完成检查时，正文只能算 draft。命中 hard blacklist、事实越界、主谓宾不成立或语体错位时，候选稿失效，不能进入交付。

改法：

- 生成前先写 prompt 合同，合同缺少语体、信息顺序、禁用骨架或项目名位置时直接 fail。
- 生成前编译已知错误禁区，把 hard blacklist、翻译腔硬骨架、模板回退和 validator 硬规则排除在候选空间之外。
- 中文事实稿必须先成立；工具、开源项目、GitHub repo、README 项目的第一句默认写成带量词的项目名定义句。如果还沿用英文定义堆砌、长定语或推荐模板，回到事实稿重写。
- 正文每个关键句都要能指出真实执行者、动作、对象和结果。
- hard validator 和人工硬清单要使用同一批规则；机器没覆盖的规则不能当作通过。
- 内部候选稿命中已知错误时，直接废弃，不能把失败句当成可润色文本。
- 复扫仍失败时，返回规则执行失败或规则覆盖缺口，不继续润色。

### 0.2 已知错误生成禁区

触发：某个结构、词组、句法骨架或批次形状已经进入 hard rule、bad sample、validator 或人工硬清单。

判断：已知错误不是“写完后再改”的对象，而是生成器不能进入的空间。最终输出如果还出现已知错误，说明执行失败；如果用户指出的问题没有对应规则，才进入规则补全。

改法：

- 生成前把已知错误列成禁区：工具项目首句缺定义、伪主语、固定推荐开头、金句式对比、裸 `不只是`、heavy-light 隐喻、长条件状语、批次前置状语过载、假口语、含混指代、批次标题重复。
- 起草时只从事实、动作、对象、结果和边界进入，不借用禁区里的句式做临时表达。
- 任一候选稿命中禁区，丢弃整句或整段，从中文事实稿重建，不做局部打磨。
- 批次输出命中同标题、同入口或同段落推进时，整批重排入口，再生成正文。
- 最终仍被用户指出问题时，先判断规则是否覆盖；已覆盖则记为执行失败，未覆盖则沉淀新规则。

### 0.3 自由生成原则

触发：规则里出现某个“好句子”，或者模型连续几次用同一种开头。

判断：结构规则不是句子模板。规则只约束主语、谓语、宾语、信息顺序、语体距离和边界清晰度，不规定第一句话必须长成什么样。

改法：

- 生成 prompt 写结构要求，不写固定开头。
- 示例句只能说明结构问题，不能作为默认写法。
- 同一类工具介绍第一句默认从带量词的项目名定义进入，第二句再从场景、动作、风险、使用路径、部署前置条件或读者任务展开。
- 不要把每条都改成 `……时 / ……后 / ……一次` 的前置状语开头。
- 单篇文章也要检查模板感；不是只有批量文案才会模板化。
- 命中 `要理解 X，我们先以 Y 为入口` 这类固定分析起手时，重写开头。

## 1. 句法层

触发：句子读起来像拼接、像翻译、像口号，或者项目名抢到了句首。

判断：先检查句子骨架，不先谈风格。自然中文可以省主语，但不能让执行者、动作对象和结果消失。

改法：

- 话题优先：先摆出讨论对象，再写动作或判断。
- 零主语：上下文已经明确时，可以省略主语；新信息不能省。
- 短分句：复杂事实拆成几个短分句推进。
- 动词中心：让动作承担推进，不让名词堆叠承担推进。
- 定语拆分：长定语改成后置说明或下一句。
- 状语位置：时间、条件、范围、顺序通常放在动作前。
- 状语边界：条件状语可以前置，但不能把多个对象、范围和风险压成一长串再拖出主句；条件过长时拆成动作句和后果句。
- 谓语完整：谓语使用完整动词短语，不能只剩 `拆`、`看`、`进` 这类单字动作。
- 体态标记：发布、接入、上线、可用、状态已经改变时，检查完成体或变化标记；缺标记会变成冷硬定义句时，补 `了`。
- 把字句：对象和处置结果都明确时再使用。
- 被字句：需要强调遭受、责任或被处理对象时再使用。

硬失败：

```text
BilldDesk 先看远控流程。
拆 BilldDesk，先从远控路径进。
```

修复方向：把真实执行者补出来，把项目名放到动作对象、定语或话题位置；谓语要写成完整动作短语，不能把示例句当成默认开头。

## 2. 信息结构层

触发：句子信息都对，但读者读完不知道为什么先看这一段。

判断：中文自然度很大一部分来自信息顺序。旧信息在前，新信息在后；场景在前，判断在后；动作在前，评价在后。

改法：

- 旧信息先出现，新信息后进入。
- 场景先出现，判断随后出现。
- 具体动作先出现，抽象评价随后出现。
- 项目名通常作为动作对象、例子或定语，不默认做主语。
- 读者任务优先于工具定义。
- 推荐理由先写它解决哪一步，再写是否值得继续看。
- 边界比空夸更可信，限制要写具体对象。
- 不用 heavy / light 隐喻概括流程和系统；把 `重 / 轻 / 偏重 / 偏轻` 改成步骤多、配置多、依赖多、审查项少、约束弱等可观察事实。

## 3. 语篇层

触发：单句都通顺，但整段像几句摘要硬拼在一起。

判断：一段中文需要推进关系。不能每段都按 `定义 -> 功能 -> 价值 -> 适用人群` 走。

改法：

- 工具项目开头先用带量词的短定义交代对象；场景和问题放到第二句之后。
- 第二句写工具介入的位置。
- 后面写具体动作、路径或限制。
- 收尾写边界，不写口号。
- 逻辑连接词能少则少，很多关系靠句序成立。
- 同一段不要频繁抽象升格。
- 批量文案要改变入口，不让每条都走同一段落顺序。

## 4. 语体层

触发：句子结构成立，但听起来像发错场合。

判断：语体不是 formal / casual 两档。不同场景需要不同句长、称呼、动作颗粒度和关系距离。

改法：

- 公文中文：信息完整，措辞克制，警惕官腔。
- 技术说明中文：对象清楚，步骤清楚，少修饰。
- 产品介绍中文：场景、动作、收益、边界依次出现。
- 社媒推荐中文：短、顺、有判断，但不能模板化。
- 熟人聊天中文：省略多，关系近，语气可以直接。
- 口播中文：短句多，节奏清楚，适合听。
- 评论区中文：判断可以靠前，但要补上下文。
- 教程中文：按步骤推进，少用抽象评价。

## 5. 口语层

触发：用户要求口语化、聊天、短文案，或输出需要像人说话。

判断：口语化不是把句子变短。真实口语依赖上下文，能省已知信息，不能省新信息。

改法：

- 已知主语可以省，新动作和新对象不能省。
- 问句可以短，但问题焦点要留下。
- 口语可以先给结论，再补理由。
- 语气轻不等于网络词多。
- 熟人语境可以直接，陌生语境要控制距离。
- 可以保留停顿和补充，但文案里不能乱模拟口误。
- `说白了`、`有点东西`、`有点意思` 这类词按假口语处理。

## 6. 翻译腔层

触发：中文词都认识，但骨架像英文产品页。

判断：翻译腔主要来自结构残留，不只来自英文词。

改法：

- 英文定义堆砌改成带量词的项目名短定义，再接中文场景句或动作句。
- 英文名词化改成中文动词推进。
- 英文长后置修饰改成中文短分句。
- 英文抽象卖点改成读者遇到的具体麻烦。
- 英文显式连接改成中文顺序承接。
- `not A but B` 类骨架改成具体动作和后果。
- `designed for / built for / powered by` 类骨架改成读者动作、工具动作或结果。

## 7. AI 腔层

触发：句子是中文，但读起来像模型在总结。

判断：AI 腔常见问题是含混指代、抽象收束、万能判断、假边界、假口语和模板节奏。

改法：

- 含混指代改成具体对象。
- 抽象收束改成具体动作或结果。
- 万能判断改成读者任务和验证点。
- 平衡句只在事实真的并列时使用。
- 边界写清测试对象，不写空提醒。
- 假口语进入 hard blacklist。
- 金句腔进入 hard blacklist。
- `拆开` 进入 hard blacklist，正文命中后必须重写。

## 8. 技术文案层

触发：材料来自 GitHub 仓库、README、工具官网、部署文档或技术项目。

判断：技术文案不能先堆技术栈。读者先需要知道它让哪条流程完整走完，技术名词要放进动作里。

改法：

- 先写流程位置，再写技术栈。
- 技术名词放在动作里，不堆成清单。
- 功能列表改成使用路径。
- `支持 A/B/C` 改成读者可以做哪些连续动作。
- 稳定性、权限、部署边界写具体检查项。
- 开源项目介绍分清学习用途、二次开发用途和生产使用边界。
- README 宣传语只能当线索，不能直接当中文结论。

## 9. 校验层

触发：文案进入发布、自动化流水线、批量生成或长期复用。

判断：黑名单只是底线。完整校验至少覆盖句法、抽象密度、修饰长度、语体、批次重复、事实落点和边界清晰度。

改法：

- hard blacklist：命中直接 fail。
- sentence skeleton：检查主语、谓语、宾语、结果。
- abstract density：检查抽象名词密度。
- modifier length：检查长定语和连续 `的`。
- register mismatch：检查语体和场景是否匹配。
- batch repetition：检查批次句式和段落顺序重复。
- fact grounding：检查有没有把事实写空。
- boundary clarity：检查限制是否具体。

## 10. Skill 核心

触发：维护本 skill、同步到全局 skill、或给其他 skill 提供中文文案底座。

判断：核心不是润色中文，也不是去 AI 味，更不是黑名单替换。核心是把事实重新组织成符合中文句法、信息顺序、语篇推进和语体距离的表达。

改法：

```text
中文结构地图
-> 语体规则
-> 场景规则
-> 技术文案规则
-> 失败样本库
-> hard validator
-> 回归测试集
```

融合原则：

- 新总图只做路由，不覆盖旧规则。
- 主谓宾结构分析是第一优先级。
- 每条新增规则都要写成触发、判断、改法。
- 能机器化的失败样本进入 validator。
- 不能机器化的结构问题进入结构标注稿和人工复核。
