# 模板回退拦截

目标：防止模型明明读了中文规则，最后还是滑回固定推荐文案。

## 1. 核心判断

单条文案也会模板化。不要只在批次里查重复。

如果一条文案去掉项目名后，像任何工具都能套用，视为未通过。

## 2. 高危推荐开头

这些开头不是永远禁用，但不能作为默认入口。出现时必须重写一版，从真实场景或具体动作进入：

- `如果你想...可以看一下...`
- `如果你想...可以重点看...`
- `想 A，可以看 B`
- `推荐一个...`
- `可以看一下...`
- `值得看 / 值得关注 / 值得拆`
- `对开发者来说...`

更好的入口：

- 直接说正在遇到的麻烦。
- 直接说工具能让用户做成哪一步。
- 直接说它现在还不适合谁。
- 直接从一个具体使用场景开始。

## 3. 高危对比骨架

拒绝这些“看起来高级”的固定对比：

- `不是 A，而是 B`
- `更值得看的不是 A，而是 B`
- `真正值得看的，是...`
- `重要的不是 A，而是 B`
- `它的价值不在 A，而在 B`
- `不是功能很多这件事，而是...`

重写时不要制造金句，直接说事实。

差：

```text
更值得看的不是功能很多这件事，而是它把 WebRTC、Electron、Flutter、Node 这一套远控链路放在一个项目里。
```

好：

```text
它把浏览器、桌面端、安卓端都接进来了。研究 WebRTC 远控时，先拆它的连接、控制和文件传输。
```

## 4. 高危收尾

这些收尾容易变成模板：

- `适合拿来研究`
- `可以作为参考`
- `完整度比较高`
- `开箱即用`
- `需要自行评估`
- `后续值得关注`

重写成具体边界：

```text
README 里已经提醒还不是稳定版。准备部署前，先压一轮连接稳定性、权限控制和设备管理。
```

## 5. 单条自检

写完后问：

1. 这段去掉项目名后，还能不能套给别的工具？
2. 有没有 `如果你想...可以...` 这种默认推荐架子？
3. 有没有 `不是 A，而是 B` 这种金句式对比？
4. 有没有 `值得 / 适合 / 参考 / 链路 / 能力` 代替具体动作？
5. 第一段有没有出现这个工具独有的事实？

任意一项命中，必须重写。
