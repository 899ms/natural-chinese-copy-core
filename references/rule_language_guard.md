# 规则语言守卫

目标：防止 skill 自己的规则文档变成 AI 腔。规则写得虚，输出一定会跟着虚。

## 1. 核心要求

每条规则必须回答三件事：

```text
看到什么 -> 怎么判断 -> 怎么改
```

如果一条规则只能表达态度，不能指导改写，就不能进入正式 reference。

## 2. 禁止的规则写法

不要把规则写成口号：

- `要 A，不要 B`
- `先 A，再 B`
- `把 XX 跑通`
- `关注 XX 链路`
- `补齐 XX 能力`
- `形成 XX 闭环`
- `提升 XX 价值`
- `落到具体场景`
- `打通全流程`

这些写法的问题是没有说明触发条件，也没有说明改句动作。

## 3. 合格规则格式

写成这样：

```text
触发：句子以项目名开头，后面接 `可以看一下`、`值得关注`。
判断：项目名被当成默认主语，读者动作和具体场景缺失。
改法：从使用场景或具体动作开头，把项目名放到动词后面。
```

或者：

```text
触发：一句话里出现两个以上 `的`，中心名词前挂了多层修饰。
判断：读者要读到句尾才知道动作，句子像英文长定语。
改法：先写中心动作，把条件、范围、技术栈拆到后一句。
```

## 4. 技术文案规则怎么写

不要写：

```text
不要先介绍技术栈，要先说它把哪条流程跑通了。
```

改成：

```text
触发：首句是 `基于 Vue / WebRTC / Node...` 这类技术栈清单。
判断：读者还不知道这个项目能完成什么动作。
改法：首句改成用户动作，例如 `浏览器能连上电脑并接管鼠标键盘`。技术栈放到下一句，用来解释画面、控制指令或文件传输怎么走。
```

不要写：

```text
功能列表必须拆成使用路径。
```

改成：

```text
触发：文案连续罗列 `多屏、文件传输、设备分组、屏幕墙、批量群控`。
判断：功能之间没有使用顺序，读者看不出先做哪一步。
改法：按实际操作顺序重排：连接设备 -> 看到画面 -> 接管控制 -> 传文件 -> 管多台设备。
```

## 5. 规则自检

写完规则后问：

1. 有没有具体触发词或句法现象？
2. 有没有说明为什么它坏？
3. 有没有给出改句动作？
4. 有没有把抽象词换成可观察对象？
5. 有没有把 bad / pass 样例分清楚？

任何一项答不上来，规则还不能入库。
