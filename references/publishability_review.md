# 可发布性人工复核

目标：补上 validator 覆盖不到的最后一关。`validate_chinese_copy.mjs` 只能证明文本没有命中已知硬规则，不能证明它已经能发。

## 1. 基本判断

最终文案必须同时满足：

- 类型正确：用户要产品更新、活动通知、社媒短帖、课程资料、发布说明时，不能写成工具介绍、规则解释或后台判断。
- 可直接发布：去掉标题和上下文后，正文仍像一段可以给目标读者看的文案。
- 信息完整：读者能看出发生了什么、和自己有什么关系、下一步要做什么或不用做什么。
- 语气自然：不是报告腔、规则日志、模型总结或客服模板。
- 没有后台痕迹：不解释为什么这么写、不暴露 validator、skill、规则、样本或审稿过程。

## 2. 常见失败

### 2.1 机器通过但不可发

触发：文案通过 validator，但读起来像规则总结、内部报告或临时改写稿。

判断：机器过关只是底线。可发文案还要看读者、渠道和文本类型。如果用户看到后还需要重新改成可发布语气，交付就失败。

改法：回到文本类型重写，不在原句上打补丁。

### 2.2 类型漂移

触发：用户要非工具类文案，输出仍然围绕“这个工具 / 项目 / repo 怎么看”；用户要产品更新、客服回复、招聘帖、事故通知、FAQ、邮件邀约或推送，输出变成规则说明或后台判断。

判断：内容方向错了，句子再顺也不能交付。

改法：先锁定类型，再写事实：

- 产品更新：新变化、用户影响、接入或使用注意点。
- 课程资料：内容安排、学习路径、卡住后怎么回看。
- 社媒短帖 / 短评：一个观察、一两个具体证据、一个自然收束。
- 发布说明 / 更新日志 / 应用商店更新：改了什么、用户会看到什么变化、是否需要操作。
- 活动通知 / 公告 / 邮件邀约 / 推送：时间、地点或形式、接收者要做什么、是否需要回复或等待。
- 客服回复 / FAQ：先回答用户当前问题，再给处理进度、边界或下一步动作。
- 营销页面 / 上手引导：读者是谁、现在卡在哪一步、下一步怎么做、做完能少掉什么重复动作。
- 事故通知 / 危机回应：发生了什么、影响谁、当前状态、用户现在要不要操作、下次更新时间。
- 招聘帖：岗位、负责事项、要求、投递方式。
- 社区更新 / 周报简报 / 会议纪要 / 视频脚本：必须保留进展、镜头或会议结论，不能只写总结性判断。

### 2.3 空判断

触发：句子只写 `重心变了`、`更现实`、`值得看`、`要单独检查` 这类判断，但没有具体动作或后果。

判断：这种句子不一定命中 validator，但读者看完不知道具体发生了什么。

改法：每个判断后面必须能接上具体对象、动作或影响。

### 2.4 多轮自检假阳性

触发：第一轮或最后一轮看起来通过，但样本类型太少，或者末尾仍有 validator warning、可发布性问题和类型漂移。

判断：调 skill 后，只看最后一条样稿不够。自进化样本必须覆盖多个真实生文类型，并要求末尾连续多轮全绿。

改法：运行 `run_self_evolution_copy_lab.mjs --require-stable-zero=3`。只有末尾 3 轮同时达到 validator hard 0、validator warn 0、publishability 0，才能把本次调校记为通过。

### 2.5 母语者自然度漏检

触发：文案通过机器检查和基本可发布性检查，但母语者仍能指出具体句子不像真人在对应场景里会写的话。

判断：只接受可复现、能落到句子的反馈。边界问题只进讨论，不直接写成硬规则；会改事实的建议必须撤回。

改法：按文本类型回到读者场景重写：

- 产品更新：如果事实有明确发布方或动作方，第一句写成 `产品名已经进了某 API` 这类标题简写时判为失败；改法是补出谁做了什么。
- 技术产品更新：`异常接手` 这类硬凑名词不要和创建、托管、调度并列；改成 `异常处理`、`人工接管` 或更具体的动作。
- 活动通知：面向参与者时少用 `未报名用户`、`补报名` 这类后台口径，改成 `还没报名的人还能继续报名`。
- 公告和设置变更：面向普通用户时，`发票抬头维护` 这类后台动词要改成 `管理`、`设置` 或页面上的真实动作。
- 营销页面：不要用 `活动报名少跑三个地方` 这类主语悬空的口号句；要写清谁少跑、少跑哪些页面或动作。
- 周报简报：收尾行动不要写成命令式的 `今天内完成报名`，改成更像提醒的表达。
- 视频脚本：画面词必须能被拍出来；`被划满的名单` 这类画面不准的词要换成 `写满改动的名单`、`被划掉一大片的名单` 等可视化表达。
- 社媒短评：`不稀奇` 单独不是错；如果后面接 `真正重要的是`、`关键是`、`这些问题会决定` 这类抬高判断，就判为英文腔风险。改法是先写具体检查项，再写结果。
- 抽象判断重排：`要判断 / 决定 / 评估 X，还得 / 需要看 Y` 判为失败。改法是把 Y 前置成具体动作，把 X 放到后面当结果，例如 `先看权限怎么批、记录怎么留、失败后谁接手，再决定这个 agent 能不能接进业务`。
- 视频字幕：`候补又对错了` 这类压缩表达会让观众分不清是“核对错了”还是“对不上”，改成 `候补名单又乱了` 或 `候补名单又对不上了`。
- 推送通知：`已改线上` 这类压缩句少了介词，改成 `改为线上`。
- 工具介绍和会议资料：`归好` 不是正常中文搭配，直接判为失败；按对象改成 `整理`、`归类`、`按议题整理`。
- 客服回复和通知：`发到短信里` 把短信写成容器，判为失败；改成 `发短信告诉你处理结果` 或 `短信会告诉你处理结果`。
- 招聘帖：`这份工作会做...` 主语和动作不搭，判为失败；改成 `工作内容包括开发...` 或 `你会负责...`。
- 会议纪要：`研发周五给...接口` 这类内部简写太糙，改成 `研发周五给出...接口` 或 `研发周五把...接口给出来`。
- 上手引导：`保存后进入...设置，打开...` 会把动作顺序粘在一起，改成 `保存后在...设置里打开...`。
- 事故通知：`导出短暂失败过一次` 这类搭配别扭，但不单独 hard；改成 `导出服务短暂出过问题`、`导出失败过一次` 或直接写受影响动作。
- 产品更新短帖：`支持筛选延期任务` 这类 `支持 + 功能` 句式不一定错，但如果整句只像功能清单，判为不可发；改成读者能做的动作，例如 `延期任务也能单独筛出来`。
- 产品更新短帖：不要写 `日会`。普通中文里改成 `每日会议` 或直接写 `开会前`。`日会前可以快速识别风险` 这类价值判断太像产品卖点；改成具体可见结果，例如 `每日会议前可以更清楚地看到哪些任务卡住了`。
- 课程资料和说明文：不要写 `比只读概念文章更容易...` 这类 `比...更...` 对比骨架。改成直接结果，例如 `代码卡住时回到对应 Notebook 看输入和输出，通常能找到卡在哪一步`。
- 社媒短评：不要用 `我更在意 / 我更关心` 开头抬判断。改成具体动作或观察，例如 `看 agent 产品时，我会先查它留下哪些运行记录`。
- agent 评估短评：不要写 `页面能跑，只说明 demo 做出来了。先看...` 这种缺主语的判断串。改成有真实动作方的句子，例如 `团队评估 agent 时应该一起看权限审批、运行记录和失败后的接手方式`。
- 产品更新和发布说明：状态变化句该补 `了` 时要补，例如 `提交成功后就能看到报名状态了`；不要写成 `提交成功后能看到报名状态` 这种缺少完成/结果语气的压缩句。
- 营销页面：前后句必须能接上因果。不要写 `不用再在 A、B、C 之间切换。运营在一个页面看 A、B、C`；改成 `因为 A、B、C 放在同一个页面，运营就可以...`。
- 招聘帖：`工作内容是...` 后面必须接职责或动作，不能只接页面、后台、系统这些对象。改写时还要检查并列层级，不能写成 `你会负责活动报名页、候补名单页面和运营后台的页面开发` 这种对象列表加后缀；具体页面和后台系统要拆开，例如 `你会负责活动报名页、候补名单页，以及运营后台里活动管理相关页面的开发`。
- 邮件邀约：不用 `走查` 这类专业/内部词，也不要写 `这次看...`。改成 `一起过一下...` 或直接写 `会议会看...`；会议链接要发出时写 `请注意查收`。
- 活动通知：`各位开发者注意` 像广播或警报，普通活动变更不要这样开头；直接写活动发生了什么变化。
- 活动通知：`现改为线上直播了` 是书面通知和口语完成态叠在一起；改成 `改为线上直播`、`改成线上直播` 或 `这次改为线上直播`。
- 活动通知：`届时也可观看` 常常是冗余公告腔。前面已经写回放会发出时，直接删掉这句。
- 外部模型审稿：模型如果把工具 / 开源项目首句里的 `一个 / 一款 / 一套` 判成冗余，不直接采纳；先回到工具定义句规则裁决。

## 2.6 老问题收口补充

- 对比骨架：`不是 A，而是 B` 在这套链路里按老问题处理，不接受“偶尔能用”的口头例外。
- 转折句式：当前偏好下，`但是 / 但 / 不过 / 然而 / 却 / 只是` 这类转折起手默认按高风险处理。除非用户明确要求保留，否则不要拿它们做文案推进骨架。
- 反例陪衬式转折：不要写 `X 能做 A，而不是 B`、`重点不是 A，而是 B`、`真正麻烦的不是 A，而是 B`。能直接写成事实、动作、结果或边界时，删掉反例半句，正面写清楚。
- 前置读者短语逗号：像 `做 X 的人，开 / 看 / 追...` 这种句子，即使 validator 已拦，人工复核时也要继续盯，避免换动词后漏过去。
- 悬空收益判断：`顺手不少`、`方便不少`、`省心不少` 这种句子不能单独当收益交付，必须落到具体动作或少掉的来回切换。
- 排查动作主谓宾：`往前追`、`往回追`、`追上下文` 不能当排查动作。问题不在禁词，而在开发者的谓语不成立；改成排查、倒查、检查、查看、定位、对照，并补出动作对象。
- 活动通知广播腔：`各位...注意` 属于普通活动通知里的老问题，继续按失败处理，不用拿语境给它找补。

## 3. 交付前人工清单

每条 final copy 交付前必须逐项回答：

- 重点核查谓语：每个关键谓语是否符合主语真实动作？有没有用虚假动作、翻译腔动词、空的方向动词、悬空改善词或容器动词补位？
- 这是不是用户要的文本类型？
- 第一段能不能让读者知道发生了什么？
- 有没有内部规则、validator、skill、审稿语言？
- 有没有只对作者有用、对读者没用的判断？
- 有没有一句话可以删掉而不影响信息？如果有，删掉或换成事实。
- 这段能不能直接发到目标渠道？

任一项为否，`publishabilityReview.status` 必须是 `fail`，不能交付。
