# 中文母语表达重构

## 定位

这个 reference 约束的是“重构表达”，不是简单润色，也不是让模型声称自己在用中文思考。

核心任务：

```text
把事实重新组织成中文母语读者更容易接收的表达。
```

允许动作：

- 调换信息顺序。
- 拆句或合句。
- 删除空话和重复。
- 把名词化结构改成动词结构。
- 把英文式主语、长修饰和模板连接词改成中文自然推进。
- 根据产品、技术、游戏、口播、社媒、剧情对白等场景调整语气。

禁止动作：

- 不得添加原文没有的事实。
- 不得添加来源里没有的日期、时间、金额、比例、版本号、文件大小、地点、人物、机构动作或发布范围。
- 不得为了显得自然而加入网络梗、情绪词或夸张判断。
- 不得保留英文原句骨架后只替换词语。

## 重构参数

每次生成或改写前，先内部确定这些字段：

- `textType`：说明文 / 产品文案 / 游戏系统文案 / 游戏剧情对白 / 公告 / 口播稿 / 社媒文案 / 技术文档 / 普通文章。
- `reader`：普通用户 / 玩家 / 开发者 / 客户 / 内部团队 / 观众。
- `purpose`：说明功能 / 引导操作 / 解释问题 / 表达情绪 / 宣传卖点 / 降低理解成本。
- `tone`：正式 / 清晰 / 自然 / 口语 / 有情绪。
- `rewriteStrength`：1 轻度润色，2 中文自然化，3 重写成稿。
- `preserveStructure`：是否必须保留原结构。

默认值：

- 用户没有指定文本类型时，用普通文章或技术说明自动判断。
- 用户没有指定语气时，用“清晰、自然、偏中文母语书面表达”。
- 用户没有指定强度时，用 `rewriteStrength = 2`。

## 信息顺序

触发：原文从抽象判断、功能定义、价值判断或技术名词起手。

判断：中文读者还没有场景和问题，直接读抽象判断会像翻译稿。

改法：把信息改成以下顺序之一：

- 场景 -> 问题 -> 做法 -> 结果。
- 读者任务 -> 工具接管的步骤 -> 限制。
- 事件事实 -> 影响对象 -> 尚未确认的边界。
- 角色动作 -> 情绪变化 -> 后果。

示例：

```text
差：通过使用该功能，用户能够更加高效地完成任务管理。
好：任务多的时候，可以用这个功能统一整理、跟进和处理。事情不容易漏，找起来也更快。
```

## 句法动作

触发：句子出现 `进行 / 实现 / 完成 / 提供 + 名词`。

判断：这类结构把动作名词化，读起来像制度说明或翻译稿。

改法：能用动词时，直接改成动词。

示例：

```text
进行资源管理 -> 管理资源
实现状态同步 -> 同步状态
完成配置 -> 配好
提供问题解决方案 -> 解决问题
```

## 场景化结果

触发：句子只写 `提升体验 / 优化流程 / 提升效率 / 赋能用户 / 打造闭环`。

判断：结果没有落到具体麻烦，读者不知道到底变好了什么。

改法：改成可感知结果，例如“少点几步”“找东西更快”“不容易漏操作”“出错后能回退”。

示例：

```text
差：该功能可以显著提升用户体验。
好：页面不用来回切，找东西会快很多。
```

不要用 `比 A 更 B` 来表达结果。能直接写结果时，直接写结果。

```text
差：回到 Notebook 看输入和输出，比只读概念文章更容易定位问题。
好：回到 Notebook 看输入和输出，通常能找到卡在哪一步。
```

## 连接词

触发：同一段连续出现 `首先 / 其次 / 此外 / 最后 / 综上所述`。

判断：连接词替代了真实推进，句子像模板报告。

改法：只保留必要的时间或步骤词，其他关系交给语序和动作。

示例：

```text
差：首先打开设置。其次选择账户。最后完成绑定。
好：先打开设置，进到账户页，然后完成绑定。
```

## 条件状语

触发：句子用 `A 一旦 B，就 C`、`当 A 进入 B 之后，真正的问题是 C` 起手，前半句包含多个对象或风险。

判断：中文可以把条件放在动作前，但条件不能压过主动作。技术介绍和项目介绍里，读者需要先知道“要做什么”或“会遇到什么麻烦”，再看条件和后果。

改法：

- 先写真实动作。
- 再写权限、范围、失败后果。
- 多个条件拆成两句。

示例：

```text
差：Agent 一旦开始碰文件、命令和外部 API，问题就不只是能不能执行，还包括权限和边界。
好：让 agent 调命令前，先把权限边界定清楚。它能改哪些文件、能不能访问外部 API、失败后怎么回滚，都要提前写进规则。
```

## 抽象判断重排

触发：句子把 `判断 / 决定 / 评估` 放在前面，再用 `还得看 / 需要看` 引出具体条件；或者先写 `不稀奇`，后面接抽象转折。

判断：中文读者更容易先接住具体动作。权限怎么批、记录怎么留、失败后谁接手，这些检查项应该先出现；能不能用、敢不敢接业务、要不要上线，适合放到后面作为结果。

改法：

- 先写具体检查项。
- 再写这些检查项影响什么决定。
- `不稀奇` 只保留在能自然承接具体动作的地方，不能后接 `真正重要的是` 或 `关键是`。

示例：

```text
差：团队要决定能不能用，还得看权限怎么批、记录怎么留、失败后谁接手。
好：团队评估 agent 时应该一起看权限审批、运行记录和失败后的接手方式，再决定能不能接进业务。
```

```text
差：页面能动不稀奇。真正重要的是权限、记录和接手。
好：团队评估 agent 时应该一起看权限审批、运行记录和失败后的接手方式，再决定能不能接进业务。
```

如果没有明确动作方，不要用 `页面能跑，只说明...。先看...` 这种判断串。把主语补出来。

```text
差：页面能跑，只说明 demo 做出来了。先看权限怎么批、记录怎么留、失败后谁接手，再决定这个 agent 能不能接进业务。
好：团队评估 agent 时应该一起看权限审批、运行记录和失败后的接手方式，再决定能不能接进业务。
```

## 硬凑动词

触发：句子里出现为了凑短句而硬压出来的动词或动作关系，例如 `归好发言和结论`、`发到短信里`、`工作会做页面`、`给接口`、`保存后进入设置，打开...`。

判断：这些句子表面能懂，但不像中文里自然的动作关系。需要判断真实动作是什么：整理、发短信告知、负责页面、给出接口、在设置里打开功能。

补充：所有动词都要优先落到真实动作。不要用英文翻译腔里的假动作顶替真实动作，例如 `往前推了一步`、`托起来`、`顺一些`、`往前追`、`往回追`、`追上下文`、`放到一条调用里接着做`。如果动词不能回答“谁在做、做了什么、作用到什么对象、结果是什么”，就按坏句重写。

硬规则：谓语必须符合主语真实动作。重构中文时，谓语不是装饰词，也不是让句子显得推进的占位符；它必须说明主语实际做了什么、作用到哪个对象、产生什么结果。

日志、报错、请求和上下文不能靠 `追` 这种谓语撑句子。问题不在某个词像不像黑名单，而在主谓宾关系不成立：开发者可以 `排查问题`、`倒查日志`、`检查请求`、`定位报错位置`、`查看前后请求`、`对照错误堆栈`，不能写成 `从一次报错往前追`。

改法：

- `归好发言和结论` 改成 `整理发言和结论` 或 `按议题整理发言和结论`。
- `把处理结果发到短信里` 改成 `发短信告诉你处理结果`。
- `这份工作会做...` 改成 `你会负责...` 或 `工作内容包括开发...`，但不能只把对象列表后面补一个 `前端开发 / 页面开发`。
- `工作内容是...页面 / 后台 / 系统` 也不对，工作内容是动作和职责，不是一个东西；改写时还要检查并列层级，不能把具体页面和后台系统混在一起。
- `你会负责活动报名页、候补名单页面和运营后台的页面开发` 这类句子仍然不合格；改成 `你会负责活动报名页、候补名单页，以及运营后台里活动管理相关页面的开发`。
- `研发周五给...接口` 改成 `研发周五给出...接口`。
- `保存后进入...设置，打开...` 改成 `保存后在...设置里打开...`。

## 轻重隐喻

触发：用 `偏重 / 偏轻 / 很重 / 很轻 / 过重 / 过轻` 评价流程、系统、工具、方案或架构。

判断：这类词来自英文 heavy / light 逻辑。中文里要写清实际负担或实际缺口，不能用一个虚形容词替代事实。

改法：

- `流程重` 改成步骤多、配置多、依赖多、启动慢。
- `流程轻` 改成检查项少、约束少、覆盖范围小。
- 需要比较时，写具体使用条件。

示例：

```text
差：如果只是写短篇，这套流程偏重。
好：只写短篇时，角色表、伏笔表和世界观规则用不上这么多；写长篇连载时，这些记录才开始有用。
```

## 主语

触发：句子反复显式写 `用户 / 玩家 / 我们`，或把 `一步 / 能力 / 链路 / 体系` 放到主语位置。

判断：中文可以省略已知主语，也更偏向让真实动作发起者或讨论对象做主语。

改法：

- 上下文清楚时省略主语。
- 操作说明可用动作开头。
- 工具项目介绍首句默认用项目名做定义句主语；第二句之后才根据需要把项目名放在定语或宾语位置。
- 抽象名词不得承担实际动作。

示例：

```text
差：用户可以点击按钮，然后用户将会看到新的页面。
好：点一下按钮，就会进入新页面。
```

## 场景语体

触发：文本类型不同，但输出都像普通说明书。

判断：语体没有贴近使用场景。

改法：

- 系统提示：短、准确、少情绪。
- 产品文案：场景、动作、结果、边界。
- 游戏系统说明：清楚、短、可执行。
- 游戏剧情对白：像角色说话，不像旁白解释设定。
- 游戏公告：事实在前，影响和时间说清。
- 口播稿：短句推进，便于听。
- 社媒文案：判断可以靠前，但不能模板化。
- 技术文档：术语准确，步骤和限制清楚。

### 产品更新短帖

产品更新要写用户能看到的变化，不要只写功能列表。

- `支持筛选延期任务` 这类句子如果只是在列功能，改成 `延期任务也能单独筛出来`。
- 不写 `日会`，改成 `每日会议` 或 `开会前`。
- `日会前可以快速识别风险` 这类价值判断太泛，改成具体场景结果，例如 `每日会议前可以更清楚地看到哪些任务卡住了`。
- 有明确状态变化时，按中文需要补 `了`；但不要为了说明时态把规则解释写进正文。

### 活动通知

活动通知要像发给参与者看的变更说明，不要像内部公告或警报。

- 不用 `各位...注意` 开头，除非真的是安全警报或紧急避险。
- `现改为...了` 同时带书面通知和口语完成态，普通活动变更里改成 `改为...` 或 `改成...`。
- `届时也可观看` 常常重复；已经写回放会发出时，直接删掉。
- 称呼要统一。`各位开发者` 和 `已报名的朋友` 混在一起时，优先改成同一种读者关系。

## 事实和数据

触发：输出里出现日期、时间、金额、比例、版本号、文件大小、地点、人物、机构动作、发布范围、维护窗口或补丁细节。

判断：中文表达可以重组事实，但不能补事实。只要来源材料没有明确给出，就不能为了让文章更完整而补一个数字、时间或事件细节。

改法：

- 来源写了具体数据，输出可以保留，但必须逐项对上来源。
- 来源没有给数据，改写成边界句，比如“材料里没有给出具体时间”或“这里只能确认它支持这项接口”。
- 需要判断影响时，先写已确认事实，再写未确认边界。
- 发布、公告、新闻、工具介绍和投资相关文案必须跑事实来源检查。

## 单字书面指代

触发：普通介绍或说明文里出现 `此工具 / 此功能 / 此项目 / 此系统 / 此平台 / 此模块 / 此方法 / 此类 / 此处`。

判断：`此` 在法律、公文、制度文本里可以成立；放到普通中文介绍里，常常像模型把“这个”压成一个字，语气过硬。这类问题优先作为口语化修正建议，不单独判 fail。

改法：

- 工具、项目、功能说明里用 `这个工具 / 这个项目 / 这个功能`。
- 类型判断里用 `这种情况 / 这类问题`。
- 位置说明里用 `这里`。
- 如果文本必须保持公文语体，再保留 `此`。

## 自检清单

生成后检查：

1. 是否逐句保留了原文结构？
2. 是否还有 `通过……来……`？
3. 是否还有 `进行 / 实现 / 完成 / 提供 + 名词`？
4. 是否还有 `A 一旦 B，就 C` 这种英语式条件状语？
5. 是否还有 `要判断 / 决定 / 评估 X，还得 / 需要看 Y` 这种抽象判断前置？
6. 是否用 `不稀奇` 接出了 `真正 / 关键 / 决定` 这种抽象转折？
7. 是否还有 `归好`、`发到短信里`、`工作会做`、`给接口` 这类硬凑动作关系？
8. 是否还有 `偏重 / 偏轻 / 很重 / 很轻` 这种 heavy / light 隐喻？
9. 是否还有空泛的 `提升体验 / 优化流程 / 赋能 / 打造`？
10. 是否一句话塞了三层意思？
11. 是否反复显式写 `用户 / 玩家 / 我们`？
12. 是否连续使用模板连接词？
13. 是否为了口语化而加入原文没有的情绪或网络词？
14. 是否删掉了术语、数值、变量名、接口名、UI 名称？
15. 读起来像中文原文，还是像翻译稿？
16. 产品更新是不是只剩 `支持 + 功能` 和价值套话？
17. 活动通知有没有 `各位...注意`、`现改为...了`、`届时也可观看` 这类公告腔？
18. 是否还有 `比...更...`、`我更在意 / 我更关心` 这类对比判断？
19. 招聘帖里 `工作内容是` 后面接的是动作职责，还是页面、后台、系统这些对象？
20. 招聘帖里是否把具体页面和后台 / 系统 / 模块混成同一层级，再用 `页面开发 / 前端开发` 当后缀补救？

## 和主谓宾规则的关系

中文母语表达重构不替代主谓宾检查。

执行顺序：

```text
先判场景和信息顺序
-> 再写正文
-> 再逐句检查主谓宾、定状补和结果
-> 再检查事实和数据是否都有来源
-> 再用 hard validator 拦截模板腔和翻译腔
```
