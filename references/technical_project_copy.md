# 技术项目文案

目标：把 README、GitHub 项目、工具对比、部署说明改成正常中文。技术项目文案的重点不是把功能列全，而是让读者知道先看哪里、能做什么、哪些地方不能直接信。

## 1. README 摘要

触发：材料来自 README，首段堆技术栈、badge、功能列表。

判断：读者还不知道项目能完成什么动作。

改法：先写用户能完成的动作，再补技术栈和限制。

## 1.1 工具介绍稿

触发：用户给出 GitHub 仓库、开源工具、产品 README，让你写一版中文介绍。

判断：介绍工具、开源项目、GitHub repo、README 项目时，第一句默认要先交代对象：`XX 是一个 / 一款 / 一套 / 一种……的……`。这不是模板腔，而是正常中文里给陌生项目建立坐标。真正要避免的是定义后继续堆 `支持 / 具备 / 提供 / 值得 / 适合`，或者写成 `XX 先看 XXX` 这种项目名硬当读者动作主语的句子。

改法：先写带量词的短定义句，再按用途展开。第一句用项目名做主语，谓语用 `是`，宾语落到工具类型、用途或所属关系；第二句开始写动作、限制或适用边界。

首句默认形状：

```text
XX 是一个 / 一款 / 一套 / 一种……的工具 / 项目 / 库 / 框架 / 插件 / 服务 / 平台 / 应用 / 界面。
```

可用：

```text
MarkItDown 是微软做的一个文档转 Markdown 工具。
Scrapling 是一个 Python 网页抓取库。
Compound Engineering Plugin 是一个把 AI 编程流程拆成命令和 agent 的插件。
```

- 学实现：先写能拆到的关键路径。
- 做二开：先写哪些模块可以改。
- 准备部署：先写必须验证的稳定性、权限和数据边界。

首句之后可以选择这些展开方式：

- 场景入口：读者现在遇到什么任务。
- 动作入口：这份代码让哪一步可以执行。
- 风险入口：使用前必须先确认什么边界。
- 路径入口：源码里哪几条路径需要分开看。
- 部署入口：启动前要准备哪些前置条件。
同一类介绍不能默认套用 `要理解 X，我们先以 Y 为入口`。
同一批介绍不能改成前置状语开头来躲开定义句，例如 `有一批材料要处理时`、`网页结构改一次`、`团队接入 agent 后`。这类写法连续出现时，比朴素定义句更像英文腔。

长稿交付时，正文后必须附结构标注稿，逐句说明主语、谓语、宾语和项目名位置。

执行顺序：

1. 先写生成 prompt，要求第一句使用 `项目名 + 是 + 量词 + 类型 / 用途 / 所属关系`，并声明项目名不能做读者动作的主语，谓语不能压缩成单字动作；不要为了避开定义句而连续使用前置状语开头。
2. 再生成正文稿和结构标注稿。
3. 用硬规则检查首句定义门禁、`项目名 + 先看`、`拆 + 项目名，先从 + 名词 + 进`、`要理解 X，我们先以 Y 为入口`、固定推荐开头、批次前置状语过载、抽象判断和稳定性空边界。
4. 如果命中 hard issue，只修失败句一轮；事实不新增，语体不改道。

## 2. GitHub Trending 推荐

触发：任务是介绍一个新冒出来的 repo。

判断：`值得关注`、`可以看一下` 这类句子没有告诉读者为什么点开。

改法：写出它和读者手头任务的关系；如果只是热闹，也要说明不用急。

## 3. 开源项目推荐

触发：项目有学习、二开、部署三种可能用途。

判断：三种用途混在一起时，文案会变成空推荐。

改法：分别写清：学什么、改哪里、部署前查什么。

## 4. 工具对比

触发：材料把新项目和 ToDesk、向日葵、Cursor、Chrome DevTools 等现成工具放在一起。

判断：不能只写“替代品”或“更适合研究”。

改法：直接分使用目标：找稳定成品、看实现、做二开、做私有部署。

## 5. 稳定性边界

触发：README 写了 beta、unstable、not production ready、实验性。

判断：`需要自行评估` 是空边界。

改法：写清要测的对象：连接稳定性、权限、数据、日志、回滚、设备管理。

## 6. 部署说明

触发：材料包含 Docker、Node、数据库、环境变量、TURN/STUN、证书、端口。

判断：配置项清单不能直接变成文案。

改法：按部署前后顺序写：准备环境 -> 配配置 -> 启服务 -> 验证关键路径 -> 查风险项。

样本见 `technical_project_cases.jsonl`。
