# 语体选择规则

目标：让同一套事实能生成不同距离、不同场景下的中文，而不是默认写成正式报告。

## 1. 默认策略

默认使用 `auto` 判断语体。若没有明确语境，落到 `plain`。

不要默认 `formal`。正式中文只是基础语体，不是自然中文的唯一标准。

## 2. 语体列表

- `formal`: 正式、完整、克制，适合报告、公告、文档、邮件。
- `plain`: 平实、清楚、正常人话，适合大多数技术解释、产品说明、推荐。
- `casual`: 日常、轻松、有关系感，适合社交媒体、群聊、轻推荐。
- `close-chat`: 熟人聊天，短句多、省略多、语气更直接。

## 3. 自动选择

按这些线索判断：

- 面向公司、客户、监管、公开文档：`formal`
- 面向普通读者、开发者、用户说明：`plain`
- 面向朋友圈、群聊、轻松种草：`casual`
- 面向熟人、连续对话、强共享语境：`close-chat`

如果事实复杂、风险高、容易误解，最多降到 `plain`，不要硬切 `close-chat`。

## 4. 用户指定优先

用户说“正式一点”“写成报告”“公文风”，用 `formal`。

用户说“自然一点”“人话一点”“别端着”，用 `plain`。

用户说“轻松一点”“像发群里”“像朋友圈”，用 `casual`。

用户说“像熟人聊天”“直接点”“随便说”，用 `close-chat`。

## 5. 距离控制

同一句事实可以有四种距离：

```text
formal: 早上好，请问有什么需要我帮忙的吗？
plain: 早上好，有什么我能帮你的？
casual: 早，有啥需要帮忙的？
close-chat: 早，干啥？
```

这不是同义词替换，而是关系距离变化：

- 越正式，成分越完整。
- 越熟，省略越多。
- 越熟，语气越直接。
- 越熟，越依赖上下文。

## 6. 降级规则

不要把严肃信息写得过于随便：

- 法律、医疗、金融风险：最多 `plain`。
- 指令、错误、失败原因：优先清楚，不要为了口语牺牲信息。
- 用户明显生气时：可以短，但不要油滑。
- 公开发布内容：除非指定，不用 `close-chat`。

## 7. 输出记录

涉及语体选择时，在 critique 中记录：

```json
{
  "selectedRegister": "plain",
  "registerReason": "default for technical explanation",
  "registerFit": "pass"
}
```
