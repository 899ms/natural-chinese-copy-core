# 中文黑名单

目标：解释 validator 里的硬拦截规则。真正的黑名单源头在 `scripts/validate_chinese_copy.mjs`，必须硬编码在那里。命中 `hard` 项时，不允许标记为 `pass`。

## 1. 使用原则

黑名单不是风格建议，是最后防线。

- `hard`: 直接重写，不解释。
- `warn`: 只有在非常具体、不可替代时才保留。
- 命中黑名单后，先重写句子入口和主干，再处理具体词。
- 修改黑名单时，先改 `scripts/validate_chinese_copy.mjs`，再同步更新本文档。

## 2. hard: 推荐模板

拒绝：

- `如果你想...可以看一下`
- `如果你想...可以重点看`
- `想...可以看`
- `可以看一下`
- `值得看`
- `值得关注`
- `值得拆`
- `拆开`
- `归好`
- `推荐一个`
- `对开发者来说`
- `对于...来说`
- `要理解 X，我们先以 Y 为入口`

常见问题：这类句子没有从事实进入，而是从推荐模板进入。

`归好` 单独列为 hard，是因为正常中文里很少这样搭配。写会议、录音、发言、结论、资料时，直接用 `整理好`、`归类好`、`按议题整理`。

## 3. hard: 金句式对比

拒绝：

- `不是 A，而是 B`
- `不只是 A`
- `不只是 A，而是 B`
- `不只是 A，还包括 B`
- `不只是 A，还要 B`
- `更值得看的不是 A，而是 B`
- `真正值得看的，是`
- `真正 X 的是`
- `真正重要的是`
- `真正麻烦的是`
- `真正难的是`
- `重要的不是 A，而是 B`
- `难点不是 A，而是 B`
- `光 A 还不够`
- `不只在 A`

常见问题：句子看起来有判断，实际没有具体动作。

总规则：不要先摆一个反例、旧判断或错误方向来托出正话。能直接写成事实、动作、结果或边界的句子，必须直接写；不要写 `X 能做 A，而不是 B`、`重点不是 A，而是 B`、`真正麻烦的不是 A，而是 B` 这类陪衬式转折。

触发：`不只是 A` 没有接具体动作，只用 `了`、逗号或句号收住。

判断：这类句子仍然在制造对比姿态，后面的判断容易滑向空结论。

改法：直接写具体动作、对象、结果或边界；不保留否定铺垫。

## 3.1 hard: 排查动作主谓宾错配

拒绝：

- `从一次报错往前追`
- `往回追日志`
- `追上下文`
- `错误很难追`

常见问题：这些句子借了英文 trace 的动作感，但中文里没有说清用户到底怎么查。问题不在词本身，而在主谓宾逻辑不成立：开发者不能靠一个空的 `追` 完成排查动作。

改法：写成 `查看前后请求`、`翻日志`、`按时间点筛选`、`定位报错位置`、`对照错误堆栈`。

## 4. hard: 英文轻重隐喻

拒绝：

- `偏重`
- `偏轻`
- `流程很重`
- `流程很轻`
- `这个系统太重`
- `这套方案过轻`
- `工具偏重配置`

常见问题：这是英文 heavy / light 逻辑残留。中文里流程、系统、方案不会因为步骤多就天然“重”，也不会因为步骤少就天然“轻”。这种说法跳过了真实问题：步骤多、配置麻烦、依赖多、启动慢、学习成本高、检查项少、约束不足。

改法：

- 写步骤数量：`要先建角色表，再写大纲，还要维护伏笔表`。
- 写操作成本：`配置项多，新项目启动前要花时间整理`。
- 写约束边界：`检查项少，容易漏掉权限和回滚问题`。
- 写适用范围：`短篇临时生成用不上，长篇连载才需要这些管理命令`。

## 5. hard: 英文条件状语起手

拒绝默认使用：

- `A 一旦 B，就 C`
- `Agent 一旦开始碰文件、命令和外部 API，问题就...`
- `当 A 进入 B 之后，真正的问题是...`

常见问题：英文常把条件从句压在主句前面，再用抽象名词收束。中文也能写条件，但自然写法通常先给具体动作或具体麻烦，再补条件和后果。条件太长时，读者还没看到主动作，就已经被一串范围、对象和风险压住。

改法：

- 先写具体动作：`让 agent 调命令前，先把权限边界定清楚。`
- 再写后果：`否则它可能改错文件、打到外部 API，出错后也很难定位原因。`
- 条件里塞进多个对象时拆句，不把文件、命令、外部 API、权限、审计都塞进同一个状语。

## 6. hard: AI 腔连接和收束

拒绝：

- `这件事`
- `这类工具`
- `这套东西`
- `这套底子`
- `这套链路`
- `这一套`
- `一层`
- `这层`
- `这几块`
- `这些东西`
- `后面都要补上`
- `旁边还补了`
- `放到实际环境`
- `无脑上生产`
- `真要`

常见问题：这些词把事实揉成一团，像模型在总结，不像人在说具体东西。

## 7. hard: 抽象名词偷懒

拒绝用这些词做主要判断：

- `能力`
- `链路`
- `生态`
- `闭环`
- `体系`
- `落地`
- `场景`
- `方向`
- `思路`
- `完整度`
- `开箱即用`
- `生产级`

保留条件：如果必须出现，下一句必须立刻写具体动作、对象和结果。`价值` 本身不是黑名单；只有当它替代事实、动作或具体收益时，才按空判断处理。

## 8. hard: 假口语

拒绝：

- `说白了`
- `有点东西`
- `有点意思`
- `这波`
- `稳了`
- `硬核`
- `狠狠`
- `拿捏`
- `咱就是说`
- `宝子`

常见问题：这些词制造熟悉感，但没有增加信息。

## 8.1 hard: 硬凑动词和容器关系

拒绝：

- `把处理结果发到短信里`
- `发到短信里`
- `这份工作会做...`
- `工作内容是...页面 / 后台 / 系统`
- `你会负责活动报名页、候补名单页面和运营后台的页面开发`
- `你会负责活动报名页、运营后台和候补名单页面的前端开发`
- `研发周五给候补名单接口`
- `保存后进入报名页设置，打开...`

常见问题：这些句子没有明显的 AI 腔词，但动作关系不对。短信不是一个装处理结果的容器；工作不能自己做页面；工作内容也不是页面、后台、系统这些对象；具体页面和后台 / 系统 / 模块不是同一层级，不能靠 `页面开发 / 前端开发` 后缀补救；内部纪要里 `给接口` 太糙，应该补出 `给出` 或 `把接口给出来`；上手引导里 `保存后进入设置，打开...` 容易让动作顺序粘在一起。

改法：

- `两个工作日内会发短信告诉你处理结果`
- `工作内容包括开发活动报名页、候补名单页，以及运营后台里的活动管理页面`
- `你会负责活动报名页、候补名单页，以及运营后台里活动管理相关页面的开发`
- `研发周五给出候补名单接口`
- `保存后在报名页设置里打开候补名单和短信提醒`

## 9. warn: 可疑但不绝对禁

谨慎使用：

- `可以先`
- `主要是`
- `适合`
- `直接`
- `比较`
- `一套`
- `多端`
- `端到端`
- `私有化部署`

保留条件：必须接具体动作或具体边界。

## 10. warn: 单字书面指代

尽量改：

- `此工具`
- `此功能`
- `此项目`
- `此系统`
- `此平台`
- `此模块`
- `此方法`
- `此类`
- `此处`

常见问题：这类表达把正常中文里的“这个 / 这种 / 这里”压缩成一个书面字，读起来像公告或翻译稿。它不是事实错误，也不单独判 fail；除非同一句还出现空泛收益、事实脑补或其他 hard issue。

改法：

- 普通介绍里改成 `这个工具 / 这个功能 / 这个项目 / 这个系统`。
- 分类判断里改成 `这种情况 / 这类问题`。
- 位置说明里改成 `这里`。
- 只有法律、制度、公文或固定表述里才保留 `此`。

## 11. 重写动作

命中黑名单后，按这个顺序改：

1. 删掉模板开头。
2. 从具体场景、动作或边界重新开头。
3. 把抽象名词改成动词。
4. 把 `这套 / 这类 / 这些 / 此` 指代改成具体对象或自然指代。
5. 用真实限制收尾，不用空判断收尾。
