# 中文工具文案好坏例

目标：提供可复用的句法形状，不提供固定模板。

## 1. 直接推荐

可用：

```text
chrome-devtools-mcp 是一个把 Chrome DevTools 接给 coding agent 的工具。

它把 Chrome DevTools 那套真工具接给 coding agent。DOM、Network、Console、性能 trace 这些原本要人盯着看的东西，现在 agent 自己就能进去查，少掉很多来回猜的时间。
```

注意：工具项目介绍默认先定义对象。`推荐一个...` 可以在聊天里偶尔用，但不作为正式即评首句。

## 2. 不要默认读者条件开头

差：

```text
UI-TARS-desktop 可以重点看一下。
```

也不要总写：

```text
如果你想让 AI 真的操作桌面应用，可以重点看一下 UI-TARS-desktop。
```

好：

```text
UI-TARS-desktop 是让 AI 操作桌面应用的项目。桌面任务看实际操作：点按钮、切窗口、处理弹窗；拆这个项目时，先看这些动作怎么接到模型输出上。
```

## 2.1 项目名不能硬当“看”的主语

差：

```text
BilldDesk 先看远控流程。
```

问题不是少了几个字，而是句法错位：`看` 的主语应该是省略的 `我们`，`BilldDesk` 不是执行者。

好：

```text
我们先看 BilldDesk 的远控流程。
```

也可以写成介绍句：

```text
BilldDesk 的远控流程可以先拆成三步：建连、传画面、接管鼠标键盘。
```

标注：

```text
主语：BilldDesk 的远控流程
谓语：拆成
宾语：三步
补语 / 结果：建连、传画面、接管鼠标键盘
判断：项目名只做定语，动作主干成立。
```

## 3. 先说真实困扰

差：

```text
这个工具提供了完整的上下文管理能力。
```

好：

```text
agentmemory 是一个保存 coding agent 项目背景的工具。长期改同一个项目时，它把这些背景留在 MCP 里，下次回来还能接着干。
```

## 4. 拆掉长定语

差：

```text
这是一个面向真实业务流程里的多 agent 协作和审批边界管理的规则集合。
```

好：

```text
Compound Engineering Plugin 是一个整理 agent 工程规则的插件。重点放在多人协作、审批边界、状态和日志这些容易漏掉的地方。
```

## 5. 把抽象判断改成具体后果

差：

```text
这类工具的价值就在这，开始接近真正的组织能力。
```

好：

```text
它把角色、审批和状态分开写清楚，团队接 agent 时不容易只停在 demo 阶段。
```

## 6. 保留边界

自然中文不是只写推荐，也要写谁不用急着看。

可用：

```text
只做一次性 demo 的人不用照着全套做。真正要把 agent 放进日常流程时，再看这类清单更合适。
```

边界句需要落到具体对象上，不能写成 `适合持续关注`、`后续值得观察` 这类空判断。
