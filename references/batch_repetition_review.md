# 批次重复度审查

目标：让一批中文文案看起来像逐条写出来的，而不是同一个模板换项目名。

## 1. 什么时候运行

只要一次处理多个 item，就运行批次审查。

单条长稿也要做模板感审查。固定起手式在一篇文章里只出现一次，也可能暴露模型在套模板。

重点看结构，不只看重复词：

- 首句结构
- 段落顺序
- 推荐动词
- 抽象收尾
- 项目名插入位置
- 星标 / 链接 / 证据句的位置
- 读者入口是否重复
- 动作类型是否重复
- 结果句是否都在说同一种空话

## 2. 开头形状配额

一批内容里，不要让超过 2 条使用同一种开头形状。

常见形状：

- `推荐一个...`
- `如果你想...`
- `如果我们想...`
- `做 X 的人...`
- `可以先看...`
- `长期做 X...`
- `要理解 X，我们先以 Y 为入口`
- `……时，`
- `……后，`
- `……一次，`

这些都是可用结构，但连续重复会变成模板。

其中 `要理解 X，我们先以 Y 为入口` 属于固定分析起手，技术介绍里默认判为 hard issue。
`……时 / ……后 / ……一次` 属于前置状语入口，单条可以成立；三条里出现两条以上时，判为前置状语过载。它不是比 `XX 是一个 XXX` 更高级的中文，只是另一种英文腔。

工具项目首句：

- 一批工具项目介绍，每条第一句默认都是带量词的项目名定义句。
- 重复风险不在 `XX 是`，而在后面都写成 `它支持...适合...`。
- 定义句后必须接具体动作、适用边界或部署限制。
- 批次变化主要放在第二句和后续段落，不靠绕开定义句制造变化。

## 3. 可互换性测试

把每条里的项目名、产品名、repo 名删掉。

如果两条剩下的文案还能互相套用，至少重写其中一条。

重点检查：

- 是否都在说 `提升效率`
- 是否都在说 `补上某种能力`
- 是否都在说 `适合进入正式流程`
- 是否都没有写出具体省掉什么麻烦

## 4. 句法入口测试

给每条文案标一个入口类型：

- `reader`: 从读者或使用者进入
- `scene`: 从具体场景进入
- `pain`: 从麻烦进入
- `action`: 从要做的动作进入
- `boundary`: 从不适合谁进入
- `object`: 从项目或工具名进入

同一批里，`object` 入口不要连续出现。`reader` 和 `scene` 可以多用，但不能让句式完全一样。

记录时写清重复位置：

```json
{
  "openingShape": "reader-if",
  "entryType": "reader",
  "repeatedWith": ["item-2", "item-5"]
}
```

## 5. 段落顺序测试

不要让每条都变成：

```text
工具介绍 -> 功能列表 -> stars -> 链接
```

可以混用：

- 先说痛点，再说工具
- 先说适合的人，再说工具
- 先说边界，再说为什么仍然值得看
- 先说具体动作，再补证据

## 6. 重写策略

发现重复时，不要只换同义词。优先换句法入口：

- 从工具入口改成读者入口
- 从功能入口改成麻烦入口
- 从推荐入口改成边界入口
- 从抽象判断改成具体动作
- 从前置状语入口改成项目名定义句，再改第二句的信息顺序

## 7. 批次交付记录

批次审查通过后，在每个 item 的 critique 中记录：

```json
{
  "batchReview": "pass",
  "entryType": "reader",
  "openingShape": "reader-condition",
  "repetitionRisk": "low"
}
```

字段名可以由下游工作流调整，但必须保留“批次已审查”的信号。

批次样本见 `batch_sample_cases.jsonl`。新增样本后运行：

```bash
node natural-chinese-copy-core/scripts/validate_batch_cases.mjs --file natural-chinese-copy-core/references/batch_sample_cases.jsonl
```
