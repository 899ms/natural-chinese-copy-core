# 中文句法规则

目标：先让句子成为正常中文，再谈风格。

## 0. 蒸馏后的底层原则

中文文案先组织话题和动作，不要照搬英文产品页的定义顺序。

优先顺序通常是：

```text
读者 / 场景 / 已知问题 -> 要做的事 -> 工具介入的位置 -> 结果 / 省掉的麻烦
```

这不是固定模板，而是检查句子有没有中文逻辑。项目名、产品名、repo 名通常应该服务于这个动作链，而不是抢成句子主语。

## 1. 中文句子主干

每个关键句必须能说清：

- 谁
- 在什么场景下
- 做什么
- 对什么东西做
- 得到什么结果
- 省掉什么麻烦

如果说不清主语、谓语、宾语或结果，重写。

## 1.1 句法骨架先行

触发：要写工具介绍、README 摘要、GUIDE、报告、长段说明，或用户明确要求结构严谨。

判断：不能只凭“读起来顺”放行。每个关键句都要先在后台拆出：

- 主语：谁执行动作。主语可以省略，但必须能从前文或场景里找回来。
- 谓语：真正发生的动作，必须符合主语真实能做的事；优先用完整动词短语，不能只剩一个含混动词。
- 宾语：动作处理的对象。
- 定语：修饰名词的信息，只能服务中心名词，不能抢走动作位置。
- 状语：说明时间、顺序、范围、条件或方式。
- 补语 / 结果：动作之后发生了什么，或者动作到什么程度。

改法：先写骨架，再写句子。骨架不成立时，不能进入润色。

硬规则：谓语必须符合主语的真实动作。禁止用虚假动作、翻译腔动词、空的方向动词或容器动词补位。检查顺序是先问“主语能不能真的做这个动作”，再问“谓语有没有明确对象和结果”。

```text
主语 / 省略主语 -> 状语 -> 谓语 -> 宾语 -> 结果
```

错误样本：

```text
BilldDesk 先看远控流程。
```

结构问题：

```text
表面主语：BilldDesk
状语：先
谓语：看
宾语：远控流程
判断：BilldDesk 不能执行“看”这个动作。真正的主语是省略的“我们”，BilldDesk 只能做“远控流程”的定语。
```

可用改法：

```text
我们先看 BilldDesk 的远控流程。
```

结构成立：

```text
主语：我们
状语：先
谓语：看
宾语：BilldDesk 的远控流程
宾语内部定语：BilldDesk 的
判断：主语能执行谓语，宾语完整，符合中文结构。
```

如果文案需要更像介绍而不是操作口令，可以改成：

```text
BilldDesk 的远控流程可以先拆成三步：建连、传画面、接管鼠标键盘。
```

结构成立：

```text
主语：BilldDesk 的远控流程
谓语：拆成
宾语：三步
补语 / 结果：建连、传画面、接管鼠标键盘
判断：主语不是执行“看”的项目名，而是可被拆解的流程。
```

### 1.1.1 主谓资格

触发：`课`、`课程`、`资料`、`文档`、`Notebook` 这类对象后面接 `往下走`。

判断：人在学习时可以“往下学”“往后看”，流程可以“继续往下跑”，但 `12 节课` 不能自己往下走。这个问题不是少一个词，而是主语和谓语不搭。

改法：把真正动作还给人，或把课程改成安排、包含、配套、覆盖这类能成立的谓语。

```text
差：12 节课按顺序往下走。
好：课程安排了 12 节内容，每节都配 Notebook。
```

```text
差：资料往下走会讲到多 agent 协作。
好：继续往后看，资料会讲到多 agent 协作。
```

### 1.1.2 排查动作的主谓宾

触发：开发者、团队或用户在排查日志、报错、请求、上下文时，用 `追`、`往前追`、`往回追`、`追上下文` 当主要谓语。

判断：这不是禁词问题，而是主谓宾逻辑不成立。开发者可以排查问题、倒查日志、检查请求、定位报错位置、查看前后请求、对照错误堆栈；`追` 在这里没有明确动作对象和结果，容易把英文 trace 硬翻成空谓语。

改法：把谓语换成真实排查动作，并补出动作对象。

```text
差：开发者可以从一次报错往前追。
好：开发者可以从错误时间点开始，查看前后请求、关联用户和服务返回值。
```

```text
差：开 issue、看文件、追上下文都会顺手不少。
好：开 issue 时可以直接看文件、改内容、查看上下文，不用来回切页面。
```

### 1.1.3 谓语完整性

触发：句子里出现 `拆`、`看`、`进`、`走`、`接` 这类单字谓语，或者一句话靠动词省略制造快节奏。

判断：单字谓语不一定错，但技术介绍、报告、README 摘要里不能让谓语只剩一个方向感。谓语必须说明动作怎么发生、以什么为入口、处理什么对象、得到什么结果。

错误样本：

```text
拆 BilldDesk，先从远控路径进。
```

结构问题：

```text
第一分句：
主语：省略，但不明确
谓语：拆
宾语：BilldDesk
判断：动作目的和拆解方式没有说清。

第二分句：
主语：省略的“我们”
状语：先、从远控路径
谓语：进
宾语：缺失
判断：`进` 不是完整谓语，读者不知道是进入项目、进入源码、进入流程，还是以某个路径作为分析入口。
```

结构修复方向：

补出真实执行者和完整谓语，把“从哪里进入分析”改成明确的动作关系。注意：下面的结构说明只用于解释语法，不是默认开头模板。

结构成立：

```text
第一分句：
主语：省略的“我们”
谓语：拆解
宾语：BilldDesk

第二分句：
主语：我们
状语：先
谓语：以……为入口
宾语 / 介词宾语：远控流程
判断：谓语短语完整，动作目的和入口都说清楚。
```

也可以把条件放进状语，让主句直接写读者动作。这个方向仍然只是结构说明，不是固定句式。

```text
拆解 BilldDesk 时，我们先从远控流程开始。
```

结构成立：

```text
状语：拆解 BilldDesk 时
主语：我们
状语：先、从远控流程
谓语：开始
补语 / 结果：进入远控流程的分析
判断：`开始` 承接前面的拆解动作，比单独写 `进` 更完整。
```

## 1.2 显性结构标注稿

触发：用户要求严格中文结构，或输出的是方案、报告、介绍稿、README、GUIDE、产品说明这类长稿。

判断：只给正文不够。需要额外给一版结构标注稿，让每个关键句的主谓宾关系可以被检查。

改法：正文后追加结构标注稿。标注格式固定为：

```text
句子：……
主语：……
状语：……
谓语：……
宾语：……
定语：……
补语 / 结果：……
结构判断：……
```

短聊天可以只做后台标注，但长稿必须显性标注。

## 1.3 体态和状态变化标记

触发：句子在写发布、接入、上线、开放、可用、变更、完成、状态已经改变，或者材料里有 `already`、`now available`、`launched`、`released`、`introduced`、`added` 这类事实。

判断：中文没有英语式过去时，但需要用体态和状态变化标记说明“动作已经完成”或“现在状态变了”。如果去掉 `了` 后句子像冷冰冰的定义句、公告标题或机器摘要，就说明完成体 / 状态变化标记缺失。

改法：

- 动作完成处补 `了`：`把 Managed Agents 放进了 Gemini API`。
- 新状态出现处补 `了`：`computer-using agents 已经正式可用了`。
- `已经` 后面如果写的是新近可用、正式上线、接入完成，通常要检查句末或谓语后是否需要 `了`。
- 一句里只在真正表示完成或状态变化的位置补，不要每个动词都补。
- 如果写的是稳定属性、长期功能或一般定义，保持定义句，不加 `了`。

差：

```text
Google 这次把 Managed Agents 放进 Gemini API。
Copilot Studio 的 computer-using agents 已经正式可用。
```

问题：

```text
第一句在写这次更新已经完成，但少了完成体标记。
第二句在写从不可用到正式可用的状态变化，但少了句末变化标记。
```

好：

```text
Google 这次把 Managed Agents 放进了 Gemini API。
Copilot Studio 的 computer-using agents 已经正式可用了。
```

结构判断：

```text
`了` 在这里不是英语过去式，而是中文里的完成体和状态变化标记。它让读者知道这不是产品定义，而是这次更新已经发生。
```

## 1.4 先作为 prompt，再作为硬规则

触发：生成正式介绍稿、批量工具文案、README 摘要、报告正文，或用户要求更严格的中文结构。

判断：句法规则不能只放在最后当黑名单。只靠最后过滤，会让初稿先按英文骨架长出来，再被动修补，修完仍然容易留下假中文结构。

改法：同一条规则用两次。

```text
第一步：作为生成 prompt，提前约束句子主干。
第二步：作为硬规则，过滤初稿里的结构错误。
第三步：把 hard issue 转成修复 prompt，只修失败句。
第四步：复跑硬规则；仍失败就报告失败原因。
```

生成 prompt 至少包含：

- 主语必须能执行谓语。
- 谓语必须是完整动词短语，不能只靠 `拆`、`看`、`进` 这类单字动词撑句子。
- 项目名不能硬当读者动作的主语。
- 关键句要能拆出主语、谓语、宾语和结果。
- 长定语要拆成短句。
- 禁止固定推荐开头和金句式对比。
- 禁止固定分析起手，例如 `要理解 X，我们先以 Y 为入口`。
- 规则只限制结构，不规定正文第一句话。
- 长稿要附结构标注稿。

硬规则过滤至少检查：

- `项目名 + 先看 / 看看 / 值得看 / 值得拆`
- `拆 + 项目名，先从 + 名词 + 进`
- `先从 + 名词 + 进`
- `要理解 + 项目名，我们先以 + 名词 + 为入口`
- `如果你想...可以看一下`
- `不是 A，而是 B`
- 抽象名词替代具体动作
- 长定语压住谓语
- 长稿缺少结构标注稿

修复 prompt 只允许改结构，不允许新增事实。

## 2. 先写中文事实稿

不要从英文 README、产品页或事实材料的顺序直接润色。先回答：

- 谁会遇到这个问题？
- 他现在想做什么？
- 这个工具帮他做哪一步？
- 它省掉什么麻烦？
- 为什么现在要打开这份材料？
- 谁不用急着看？

中文事实稿不是最终文案，但它必须已经读得顺。事实稿别扭，最终文案也会别扭。

## 2.1 前置条件不单独顿开

时间、条件或读者范围可以放到主动作前，但不要把它写成长状语再用逗号隔开。逗号会把主动作推迟，读者先读到条件，后面才等到句子真正要说什么。

差：

```text
刚补 Agent 基础的人，先按章节跑工具调用、规划和多 agent 协作。
```

好：

```text
刚补 Agent 基础的人可以先按章节跑工具调用、规划和多 agent 协作。
```

差：

```text
下载模型前，先查本机硬件、模型规格和 provider 选择。
```

好：

```text
下载模型前先查本机硬件、模型规格和 provider 选择。
```

## 3. 项目名不是默认主语

项目名、产品名、repo 名通常是被推荐对象，不是中文句子的天然主语。

差：

```text
UI-TARS-desktop 可以重点看一下。
```

好：

```text
如果你想让 AI 真的操作桌面应用，可以重点看一下 UI-TARS-desktop。
```

项目名只有在它真的执行动作时，才适合做主语。

```text
Bun 又冲上了 GitHub Trending。
```

## 4. 开头规则

工具、开源项目、GitHub repo、README 项目介绍的第一句，默认用项目名定义句。读者第一次看到陌生项目时，先知道“它是谁、做哪类事”，后面才好读动作、边界和部署限制。

默认首句：

```text
项目名 + 是 + 量词 + 类型 / 用途 / 所属关系
```

可用：

```text
MarkItDown 是微软做的一个文档转 Markdown 工具。PDF、Office 文档和网页先转成 Markdown，再交给 LLM 处理。
Scrapling 是一个 Python 网页抓取库。页面结构变了，它会按相似度把之前抓过的元素找回来。
Compound Engineering Plugin 是一个把 AI 编程流程拆成命令和 agent 的插件。需求讨论、执行、审查和经验记录都能放进同一个工作节奏里。
```

不要用这些句子替代工具项目首句：

- `这个项目是一个...`，没有写出项目名。
- `这个工具是一个...`，没有写出项目名。
- `Repo 可以看一下`
- `想...可以...`
- `长期让...`
- `给...时，可以...`
- `如果你想...可以看一下...`
- `对开发者来说...`
- `值得看 / 值得关注 / 值得拆`

首句定义也不能写成宣传词：

```text
MarkItDown 是一个强大、易用、完整的文档处理工具，具备多格式转换能力，值得关注。
```

不要把下面这些结构当万能模板：

- `如果你想...`
- `如果我们想...`
- `做 X 的人，可以...`
- `推荐一个...`

这些结构可以在后文偶尔用，但不能抢第一句。首句先定义对象，第二句再写具体场景、具体动作或具体麻烦。

也不要为了躲开定义句，把每条都写成前置状语：

```text
有一批材料要处理时，……
网页结构改一次，……
团队把 agent 接进开发流程后，……
```

这种连续开头会把主动作推到后面，读起来像英文条件从句换了中文词。工具项目介绍里，第一句先回到项目名定义句。

首句之后的展开方向：

- 先说具体场景：`远程控制这类工具，最麻烦的是连接、权限和设备管理。`
- 先说具体动作：`BilldDesk 把浏览器、桌面端和安卓端都接进来了。`
- 先说边界：`只想找一个稳定商用远控工具的人，可以先等等。`
- 先说真实麻烦：`自建远控服务时，屏幕传输只是第一步，后面还要管设备、权限和文件传输。`

## 5. 修饰语规则

少写长定语，少连续 `的`。长定语通常说明句子还没有分句处理。

差：

```text
这个支持多模型上下文管理的自动化协作能力工具...
```

好：

```text
它主要解决多模型协作时的上下文管理问题。
```

处理顺序：

1. 找中心名词。
2. 只保留最必要的一个修饰。
3. 其他信息拆成下一句。

高风险症状：

- 一个名词前堆了两层以上修饰。
- 一句话里连续出现多个 `的`。
- 读到句尾才知道真正动作。
- `能力`、`体系`、`方案`、`工具` 前面挂满名词。

重写动作：

```text
先写它做什么，再把条件、范围、限制拆到后一句。
```

差：

```text
这个面向真实业务流程的多 agent 协作审批边界管理方案...
```

好：

```text
它整理的是多 agent 进业务流程前要先说清的规则。重点是审批边界、状态记录和失败时谁来接手。
```

## 6. 动作和结果要具体

多用能执行、能观察到结果的动作：

- 接进去
- 跑起来
- 管起来
- 看清楚
- 留得住
- 省掉来回解释
- 少踩配置坑

少用悬空判断：

- `提升能力`
- `形成闭环`
- `完善体系`
- `推进落地`
- `释放价值`

能写具体动作，就不要写抽象判断。

英文材料常把动作名词化。改中文时，要把名词重新还原成动词。

差：

```text
它提供上下文管理能力。
```

好：

```text
它把项目背景留住，让 agent 下次还能接着改。
```

检查方法：

- `管理` 能不能改成 `记住`、`同步`、`分成几步处理`、`接进去`？
- `支持` 后面是不是只跟功能名，没有用户动作？
- `能力` 前面的词能不能变成一句具体动作？

## 7. `把` 字句只在真的处理对象时用

`把` 字句需要明确对象和明确结果。

可以：

```text
它把 Console、Network、DOM 这些调试信息交给 agent 看。
```

不自然：

```text
它把多 agent 工作流做成了组织能力。
```

遇到 `把 A 做成 B`、`把 A 放进 B`、`把 A 往 B 推`，优先重写成更直接的中文动作。

## 8. 抽象名词降级

少用：

- `价值`
- `方向`
- `思路`
- `能力`
- `链路`
- `生态`
- `闭环`
- `体系`
- `落地`
- `信号`

如果必须使用抽象词，下一句要立刻说明具体动作或具体后果。

## 9. 自检问题

写完逐条问：

1. 这句话能不能直接发给朋友？
2. 去掉项目名以后，还像不像正常中文？
3. 有没有英文产品页的句子骨架？
4. 有没有具体说清它省掉什么麻烦？
5. 有没有假口语、金句感、模板感？
6. 主语、谓语、宾语或结果能不能被直接指出来？
7. 有没有长定语把中心动作藏起来？
8. 有没有把英文名词化结构直接搬进中文？
9. 项目名能不能执行句子里的谓语？如果不能，它应该改成定语、宾语内部信息或话题。
10. 谓语是不是完整动词短语？有没有用单字谓语省略掉入口、对象或结果？
